# AGENTS.md

Conventions and gotchas for working in this repo, gathered from hands-on sessions. Read this before making non-trivial changes — several of these aren't obvious from the code alone.

## What this is

Tagstash is a **live SaaS with real users and real Stripe billing** (hosted at tagsta.sh). Treat prod data, migrations, and billing code with care — this isn't a toy project. See `README.md` for the feature/tech overview.

## Backend: single-file dispatcher

All API logic lives in one file: `functions/api/[[path]].js`. There's no router library — `onRequest` splits the URL into `segments` and dispatches by `segments[1]` to a `handleX` function (`handleAuth`, `handleBookmarks`, `handleProfiles`, `handleBilling`, `handleSupport`), each an if-chain branching on `request.method` + further segments. A new route means either a new branch inside an existing `handleX`, or a new top-level `handleX` wired into `onRequest`'s dispatch.

Auth pattern: every protected branch starts with

```js
const auth = await requireAuth(request, env);
if (auth.error) return auth.error;
```

Routes that must be reachable by anonymous visitors (like the public profile endpoint) need their own handler that never calls `requireAuth` — don't add them as a branch inside `handleBookmarks`/`handleAuth`, since those call `requireAuth` unconditionally at the top.

`GET /api/health` is a sixth top-level route, but it's handled inline inside `onRequest` itself (not a `handleX` function), and deliberately checked *before* the `env.DB` binding check — so it works as a liveness probe even without D1 configured.

There's also a Pages Function outside the `/api` dispatcher entirely: `functions/sitemap.xml.js` serves `GET /sitemap.xml`, listing a few hardcoded static pages plus the public profiles that pass the indexing bar (see "Profile moderation and the indexing bar" below).

`GET /api/profiles/:username` (in `handleProfiles`) is a **stable, documented public API** meant for third-party consumption — Settings surfaces ready-to-copy URLs (including per-tag `?tag=` filters) for users to embed on other sites, and it's documented in `README.md`. Treat changes to its response shape as a compatibility concern, not a free internal refactor.

## Security headers and CSP (`public/_headers`)

`public/_headers` sets the CSP, HSTS, `nosniff`, `X-Frame-Options`, `Cross-Origin-Opener-Policy: same-origin`, `Referrer-Policy` and `Permissions-Policy` on every static asset, plus immutable caching on `/assets/*`. Pages applies `_headers` to static assets only, but `functions/index.js` and `functions/u/[username].js` call `next()` and re-wrap the asset response, so the SSR'd `/` and `/u/*` inherit the headers too. COOP is safe only because Stripe Checkout and the billing portal are full-page navigations (`window.location`), Turnstile is an iframe and nothing uses `window.open`/`opener`; a future popup-based flow (OAuth, Stripe popup) would need `same-origin-allow-popups`. HSTS deliberately has no `preload` yet. Styles use `style-src 'self'`: keep page styles in same-origin CSS files and classes, including SSR/prerender output and parsed HTML/SVG strings. React `style={{...}}` props and direct CSSOM property assignments work under this policy, but parsed `style="..."` attributes and runtime `<style>` injection do not. Email HTML is delivered separately and is unaffected by the site's CSP.

`/api/*` responses are built by the Worker and get none of `_headers`. Instead `withApiHeaders` in `functions/api/[[path]].js` stamps every response — success, error, the CSRF 403, the catch-all 500 and `onRequestOptions` preflights — with `Cache-Control: no-store` (the one exception is a successful public profile response, see "Public profile edge cache" below), `nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, a `default-src 'none'; frame-ancestors 'none'` CSP, and HSTS on HTTPS requests, then applies CORS via `withCors`/`corsHeadersFor`. Route new response paths through `onRequest` rather than returning around it. `tests/api-headers.test.mjs` covers the paths. CORS is an allowlist (`ALLOWED_ORIGINS` + `APP_URL` + any `moz-extension://`): the matching `Origin` is echoed back with `Vary: Origin`, and anything else gets no `Access-Control-Allow-Origin`. The browser extension normally bypasses CORS through its `host_permissions`; its Chrome ID and the Firefox scheme are listed only so installs whose site access was revoked keep working. If the extension ships under a new store ID (e.g. Edge), add it.

The CSP is an enforced allowlist built from what the app actually loads: `'self'`, Google Tag Manager/Analytics (loaded only after cookie consent), Google favicons (`www.google.com` redirecting to `*.gstatic.com`), and Cloudflare Turnstile (script + iframe). Fonts are self-hosted (`font-src 'self'`; see the theme section), so no font CDN belongs in the CSP. There is **no `'unsafe-inline'` for scripts or styles**. If you add a third-party script, image host, iframe or `fetch` target, add its origin to the matching directive, and update the Third-Party Services section of `PolicyPage.jsx` if it touches user data. Check new libraries for injected styles before adopting them; don't restore `'unsafe-inline'` to accommodate one. A blocked resource shows up as a CSP error in the browser console, not in the build. The accessibility audit also fails on style CSP violations; use `--check-third-parties` for the consent/GA and Turnstile checks (build with the public Turnstile test site key `VITE_TURNSTILE_SITE_KEY=1x00000000000000000000AA` in an ignored `.env.local`). That pass loads real vendor scripts but intercepts analytics collection so test visits aren't sent to the production property.

The public profile API is consumed cross-origin by other sites (orboro.net and Hidden Lodge fetch it server-side in Astro SSR/build code, so they aren't subject to CORS or CSP at all). `corsHeadersFor` keeps `Access-Control-Allow-Origin: *` on `/api/profiles/*` while the rest of the API uses the allowlist — that endpoint is public by design.

### Public profile edge cache

`GET /api/profiles/:username` is the only API response that is not `no-store`. **Cloudflare does not cache Pages Functions responses from `Cache-Control`/`s-maxage` alone**, so `handleProfiles` uses the Workers Cache API (`caches.default`) explicitly: `match` before any D1 query, and `put` of the 200 body via `runAfterResponse` (`context.waitUntil`) with a 60 s TTL. Details that matter:

- **Key** = a synthetic GET on the request's origin: `/api/profiles/<username, ASCII-lowercased>` plus the normalized `?tag=` list (trimmed, lowercased, de-duplicated, first-seen order, because `appliedTags` is echoed in the body). Cookies, `Authorization`, `Origin` and every other query parameter are not part of it, so a cache-buster can't bypass or flood the cache. Only ASCII is folded because the lookup uses SQLite `LOWER()`. More than 10 tag filters (or one over 100 chars), or extra path segments, are served uncached.
- **Only 200 bodies** are stored or served from cache. Missing/private/suspended 404s, 5xx and every other route stay `no-store`. `withApiHeaders` swaps in `Cache-Control: public, max-age=0, s-maxage=60` only for a Response object `handleProfiles` flagged (`cacheablePublicProfiles`) that is a 200 GET on `/api/profiles/<one segment>`. `max-age=0` keeps browsers and other private caches revalidating (a profile turned private is never pinned in a client); `s-maxage=60` lets a shared cache hold it for the same minute as the Cache API entry. Only the *body* is cached: security headers, `Access-Control-Allow-Origin: *` and `Vary: Origin` are rebuilt on every response, hits included. Hits and misses carry `X-Tagstash-Cache: HIT|MISS` (absent when there is no Cache API) for debugging.
- **Identity**: the body never depends on the requester. `handleProfiles` doesn't read cookies/Authorization/Origin, and owners and admins see the same body as anonymous visitors. Keep it that way: if a viewer-specific field is ever added, bypass the cache (or key on it) first. The CSRF/web-origin gate in `onRequest` still runs before the cache lookup.
- **Feature-detected**: no `caches` global (node test harness) or any cache error means a plain uncached response. Local `wrangler pages dev` does emulate the Cache API, so hit/miss can be checked with curl. `tests/profile-cache.test.mjs` installs a fake `caches.default`.
- **Staleness**: a profile can be served for up to 60 s after it goes private, is suspended, or its bookmarks/tags change (bookmark edits, deletes and private toggles do **not** purge). Best-effort purge runs for `PUT /auth/profile-public` (turning off), admin `suspend` / `make-private`, `PUT /auth/username` (old name) and admin account delete: it deletes the base URL and the single-tag variant for each tag on the user's public bookmarks. Multi-tag variants just expire. The Cache API is per data center and `cache.delete` only reaches the data center that handled the request, so other locations can serve a stale copy until the TTL runs out; a put racing a purge in the same data center can also re-store a stale body for at most 60 s. Don't promise instant takedown in copy.
- **Rate limiting**: no Cloudflare rate-limit rule covers this endpoint. The free plan allows one rule and it is used for the login brute-force limit (`POST /api/auth/login`, 5 req/10 s per IP, block 10 s). Profile API protection relies on this 60 s edge cache.

## Server-rendered pages outside the API

Two Pages Functions rewrite the SPA shell's HTML before it reaches the browser: `functions/index.js` (homepage marketing copy + `SoftwareApplication`/`FAQPage` JSON-LD) and `functions/u/[username].js` (per-profile title/description/OG tags). The homepage SSR content sits in a `<main id="main">` so it has a landmark before React mounts (axe `region`/`landmark-one-main`; the audit scans it with scripts blocked). React hydrates over the result, so the SSR'd DOM and `Home.jsx`/`useDocumentMeta.js` must agree — change copy or titles in both places. Both bail out (returning the untouched response) for non-200 or non-HTML responses. `/u/:username` answers a missing, non-public or suspended profile with a real **404** (SPA shell kept as the body so the app renders its not-found UI, plus `noindex`) and a failed D1 lookup with **503**; a public profile below the indexing bar is a 200 with noindex; canonical, `og:url` and JSON-LD use the *stored* `users.username` casing, not the URL's (`PublicProfile.jsx` does the same client-side). Only for **indexable** profiles it also inserts a static snapshot of the newest 100 public bookmarks as `<div id="ssr-profile">` **just before** `#root` (never inside it; `#root` stays empty and belongs to React). It lists them newest first, matching the profile page's default sort, and mirrors the loaded page: header, toolbar-height spacer, `@username's bookmarks` heading, each bookmark's title, domain and tags linked with `rel="ugc nofollow noopener"`, and a footer with the report link. That costs one extra D1 query (bookmarks + `json_group_array` tag names), run only on the indexable path. If it fails the page falls back to metadata only (still 200), never a 503. Every user-controlled value goes through `escapeHtml`, and only `http:`/`https:` URLs (via `safeHttpUrl`) become links; anything else renders as plain text. **Handoff:** `#ssr-profile + #root { display: none }` (App.css) keeps the app hidden while it mounts and loads behind the snapshot, so visitors never see the Suspense/"Loading profile..." states. `src/utils/profileSnapshot.js` removes it: `PublicProfile` in a layout effect once `loading` is false (list, not-found or error committed, before paint); `App` as soon as the route differs from the first-loaded path; and `ErrorBoundary` on a crash. Without JS the snapshot simply stays. Don't remove it in an effect cleanup: StrictMode's dev double-mount would drop it immediately. The markup uses only global `App.css`/`index.css` classes (`#root` box rules also cover `#ssr-profile`). Keep any class it needs out of lazy-loaded component stylesheets, and update `renderProfileBookmarks` if `DefaultCard`, `AppHeader`/`AppFooter` or the profile header change. `tests/profile-ssr.test.mjs` covers it, including hostile titles/tags/URLs.

`/features`, `/privacy` and `/support` are prerendered at build time by `scripts/prerender-features.mjs` into `dist/*.html` (Pages serves them extensionless): `/features` gets full body markup, `/privacy` and `/support` only a rewritten `<head>` (title, description, canonical, OG/Twitter) because their bodies are interactive. Head text lives in `FEATURES_META` (`src/utils/featuresMeta.js`) and `PRIVACY_META`/`SUPPORT_META` (`src/utils/pageMeta.js`), shared with `useDocumentMeta`; the head rewrite is `scripts/page-head.mjs`. A new indexable static page needs an entry there **and** in `functions/_middleware.js`'s `PAGE_PATHS` (everything else gets a 404 + noindex). The sitemap's profile `lastmod` is the newest *public* bookmark's `created_at`/`updated_at` (not `users.updated_at`). `robots.txt`, `llms.txt` and the sitemap are the other crawler-facing surfaces; keep `llms.txt` current when pricing or features change.

## Input limits and request validation

Every write route validates its **whole** payload before touching D1, then commits related writes in one `db.batch()` (D1 runs a batch as a transaction). Invalid input answers 400 and leaves the prior row and its `bookmark_tags` untouched; `tests/input-limits.test.mjs` pins this. Follow the same shape for new routes: validate → build statements → one batch.

- **Bodies:** `parseBody(request, { maxBytes })` streams the body and throws `HttpError` (413 over the cap — 256 KB by default, `MAX_IMPORT_BODY_BYTES` 8 MB for import; 415 unless `application/json`/`+json`; 400 for invalid JSON or a non-object). `routeRequest`'s catch turns `HttpError` into a JSON response. An empty body is still `{}`.
- **Limits** live in `INPUT_LIMITS` in `functions/api/[[path]].js`: title 1000, URL 8192 (after normalization), description 10000, tag 100 chars, 50 tags per bookmark, username 50, email 254, new passwords 8 characters minimum / 72 UTF-8 bytes maximum (`passwordMinChars`/`passwordMaxBytes`, see "Password policy" below; passwords being *checked* at login or re-entry have no length limit beyond the body cap), API key name 100, 2000 rows per import, 500 bookmark ids per bulk request (`bulkBookmarkIds`). (The API-key count limit is `MAX_ACTIVE_API_KEYS_PER_USER`, with the API-key helpers — not duplicated here.) The user-facing ones are mirrored in `src/utils/inputLimits.js` for `maxLength` and the tag checks in `App.jsx`; a test fails if the two drift.
- **Types:** fields must be the documented type — a number where a string belongs is a 400, never coerced or silently skipped. Bookmark create/update go through `validateBookmarkInput` (`tags`: omitted = keep, `null` = clear, otherwise an array of single-word strings). Tag writes use `upsertTagNamesStatement`/`linkTagNamesStatement` inside the caller's batch, never per-tag round trips.
- **Per-account budgets** for expensive routes are `USER_RATE_LIMITS`, counted from `auth_events` by `user_id` via `isUserBudgetExhausted` (metadata lookups 60/10 min and 1000/day; imports 20/hour). Same soft-limit and fail-open semantics as `AUTH_RATE_LIMITS`; these rows are pruned after a day and hidden from the admin auth log. `0017_user_budget_index.sql` only adds the index they use.

**Bulk import** (`POST /bookmarks/import`) validates every row first, then writes accepted rows in chunks of 250, each one batch of three statements: upsert the chunk's tag names; insert its bookmarks with the free-plan guard inside the statement (paid, or `key < 50 − current count`, so concurrent imports and saves can't share the same remaining slots), in descending key order so each row's id is `MAX(id) − key`; then link tags for the admitted rows only (`bm.key < changes()`, so the link statement must stay directly after the insert), with the join re-checking owner and URL. Rows are skipped as `invalid` (with `invalidRows` reasons), `duplicates` (already saved, or repeated in the file), or over the free-plan limit (`limitReached`); over-long titles/descriptions are truncated (`truncated`) and bad/surplus tags dropped (`droppedTags`). A chunk lands whole or not at all; if one fails the response is a 500 with the counts so far, and re-importing the same file is safe. The response keeps `imported`/`skipped`/`limitReached`/`membership_tier`/`bookmark_limit` for `Import.jsx`; the rest is additive.

## Scraped page metadata: decode entities, don't trust the regex

`fetchSiteMetadata` only fetches public http(s) destinations: it refuses credentials in the URL, `localhost`/single-label/`.local`/`.internal`-style names and private, loopback, link-local, CGNAT, multicast and IPv4-mapped/NAT64 IP literals; follows at most 5 redirects **by hand** (`redirect: 'manual'`), re-checking each `Location`; requires `text/html` or `application/xhtml+xml`; and streams at most 512 KB, stopping at `</head>`, all under the 8-second deadline. Hostnames are not DNS-resolved (Workers has no resolver and can't reach private networks anyway), so a public name pointing at a private address is only stopped by the platform. Scraped titles/descriptions are clamped to the bookmark limits.


`fetchSiteMetadata` / `extractPageTitle` / `extractMetaDescription` scrape titles and descriptions out of raw HTML with regexes (Workers has no `DOMParser`). Two things bite here:

- **HTML attribute values arrive entity-encoded.** A page serving `theorycraft &amp; simulations ... don&#x27;t` would otherwise persist those escapes into D1 verbatim and show them raw in the edit form. Everything scraped goes through `cleanScrapedText` (decode → collapse whitespace → trim), which uses the local `decodeHtmlEntities` helper + `HTML_NAMED_ENTITIES` table. Add new named entities there rather than decoding ad hoc at a call site, and keep it a **single** decode pass — decoding repeatedly is how `&amp;lt;` turns into a real `<`.
- **The meta-tag patterns capture the opening quote and back-reference it** (`content=(["'])([\s\S]*?)\1`, value in group **2**, not 1). The earlier `[^"']+` form truncated at the first apostrophe, so `Tom's diner & bar` stored as `Tom`. Preserve the back-reference if you add more patterns.

The browser extension's popup reads meta tags from the live page DOM (already decoded) and only falls back to this endpoint, so it inherits fixes here for free. The frontend also has its own `src/utils/decodeHtmlEntities.js` (textarea-based) applied at *display* time and when opening the edit form — that's legacy-data cover for rows saved before the backend decoded, not the primary fix. Such rows self-heal when edited and saved.

## Email sending: Cloudflare Email Sending (not Resend)

All transactional email goes through the **Cloudflare Email Sending REST API** (no SDK, plain `fetch`) via the `sendEmail` helper in `functions/api/[[path]].js`, used by `sendVerificationEmail`, `sendPasswordResetEmail`, `sendExistingAccountNotice` (sign-up with a registered address), the email-change mails, and the support-form handler. Config is `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID` / `EMAIL_REPLY_TO` / `SUPPORT_EMAIL` (see `.dev.vars.example`). `sendEmail` throws if the token/account ID are unset, and callers turn that into a `503`.

Each email purpose has its own "from" address via `emailFrom(purposeVar, fallback, env)`:

- `EMAIL_FROM_VERIFICATION` (default `welcome@tagsta.sh`)
- `EMAIL_FROM_PASSWORD_RESET` (default `support@tagsta.sh`)
- `EMAIL_FROM_CONTACT` (default `contact@tagsta.sh`) — the support form's outgoing *sender*, not to be confused with `SUPPORT_EMAIL`, the inbox it delivers *to*.

Each falls back to the generic `EMAIL_FROM` before its hardcoded default, so self-hosters on another domain can override with one var instead of three.

## Fixed upstream calls: deadlines, 502/503, idempotency

Email, Turnstile siteverify and Stripe go through `fetchUpstream(service, url, options)`, which adds an `AbortSignal.timeout` deadline from `UPSTREAM_TIMEOUT_MS` (email 10s, Turnstile 5s, Stripe 15s, Pwned Passwords 3s) and turns network failures/timeouts into `UpstreamError`. `sendEmail` and `stripeRequest` also throw `UpstreamError` for provider error responses (Stripe's message is kept, so `isStripeMissingResourceError` still works). The status convention: **503** = not configured (`EmailNotConfiguredError`, missing Stripe/Turnstile keys), **502** = the provider failed or timed out. `routeRequest`'s catch answers any uncaught `UpstreamError` with a 502 and a per-service message; routes that report send failures use `emailFailureStatus(error)`. Don't add a bare `fetch` to a fixed upstream. (`fetchSiteMetadata` fetches arbitrary user URLs and has its own handling.) The Pwned Passwords check is the one upstream that **fails open**: `isPwnedPassword` catches every error and accepts the password, so it never produces a 502.

Object-creating Stripe POSTs (`/customers`, `/checkout/sessions`) send an `Idempotency-Key` from `stripeIdempotencyKey(purpose, userId, parts)`: user id + hour bucket + a hash of the exact parameters, so a retry after a timeout gets the original object back, while different parameters never reuse a key (Stripe rejects that). Checkout keys also hash `users.updated_at`, which the webhook bumps, so a completed session is never replayed. Recreating a customer Stripe no longer knows passes the stale id into the key so the deleted customer isn't replayed. Customer updates and portal sessions send no key.

## Turnstile: success, hostname and action

`verifyTurnstile(request, env, token, expectedAction)` accepts a token only if siteverify says `success: true`, the `hostname` is the request's own host or `APP_URL`'s (`turnstileHostnames`; covers Pages previews), and `action` matches. The support widget renders with `action: 'support'` (`TURNSTILE_SUPPORT_ACTION`); keep `SupportPage.jsx` and the constant in sync. Local HTTP requests skip only the hostname check, since test sitekeys report a placeholder hostname.

Integration notes ([REST API docs](https://developers.cloudflare.com/email-service/api/send-emails/rest-api/)):

- `POST https://api.cloudflare.com/client/v4/accounts/{account_id}/email/sending/send`, `Authorization: Bearer <token>`, token scoped to `Email Sending: Edit`.
- Reply-to is the **snake_case top-level field `reply_to`** — confirmed by live testing. `replyTo` 400s with `invalid_request_schema`, and a `headers: { 'Reply-To': ... }` object 400s with `email.invalid`; neither is documented clearly, so don't reintroduce them. The support form's "reply goes to the requester" behavior depends on this.
- 5 MiB total message size limit (incl. attachments); rate-limited (error code 10004).
- Beta product — the `from` sending domain must be connected/verified in the Cloudflare dashboard first.
- Migrated from Resend on 2026-08-02; the `resend` npm package is gone from `package.json`.

## D1 migrations: guard new columns, don't assume they exist

Cloudflare Pages deploys the Worker bundle **independently** of `wrangler d1 migrations apply` — there's no auto-migrate-on-deploy hook, so code can reach prod before its migration has been applied there. For any path that references a newly-added column *by name* (filtering, inserting, toggling — not `SELECT *`), guard it:

```js
const hasFoo = await bookmarksTableHasColumn(db, 'foo'); // or usersTableHasColumn
```

and fail closed (404/503) rather than letting an unguarded reference 500 every request that touches that table. `is_favorite`, `is_private`, `profile_public`, `theme`, `link_target`, `last_login_at` and `suspended_at` all follow this pattern — copy it for new boolean/nullable columns on `users` or `bookmarks`. (`0007_password_reset.sql`'s `password_reset_tokens` table is the one deliberate exception — narrow blast radius, only two rarely-hit routes.) Note `is_favorite` on `bookmarks` is guarded via a pre-fetched `PRAGMA table_info` set (`bookmarksColumnNames.has('is_favorite')`) rather than a direct `bookmarksTableHasColumn` call at that site — same pattern, different idiom.

Per-bookmark boolean toggles (favorite, private) share one backend helper, `toggleBookmarkFlag(db, userId, bookmarkId, columnName, messages)`, and one frontend helper, `handleBookmarkToggle(apiCall, id, fallbackErrorMessage)` in `App.jsx` — extend those for the next toggle instead of copy-pasting a route/handler pair. `getTagsByBookmarkId(db, userId, { publicOnly, hasIsPrivateColumn })` is the same idea for the tag-join query.

Migrations are sequential numbered files in `d1/migrations/`, applied via `npm run setup:db` locally.

## Free-plan bookmark limit is enforced in the INSERT

`FREE_BOOKMARK_LIMIT` (50) is enforced by `insertBookmarkWithinPlanStatement`, which does `INSERT … SELECT … WHERE tier = 'paid' OR (SELECT COUNT(*) …) < 50` as one statement inside the create batch (`meta.changes` is 0 once the limit is reached, and the tag-link statement after it is gated on `changes() > 0`). A separate count followed by an insert lets parallel saves overshoot. `POST /bookmarks` keeps a cheap pre-check for the error message, but the conditional insert is the control. `POST /bookmarks/import` applies the same guard per chunk (`importChunkStatements`), so concurrent imports and saves share the limit; `tests/free-plan-limit.test.mjs` and `tests/bookmark-import.test.mjs` cover the races with `queryLatency`.

## The `tags` table is global, not per-user

`tags` (`d1/migrations/0001_initial.sql`) has a single global `UNIQUE` `name` column and **no `user_id`** — it was never made per-user in any later migration. One tag row (e.g. id 15, `gaming`) can be shared by many users' bookmarks simultaneously; per-user scoping exists only one level down, via `bookmark_tags` joined to `bookmarks.user_id`. This matters for any endpoint that mutates or deletes a `tags` row directly (rename, delete, merge — see `POST /bookmarks/tags/merge` for the reference pattern):

- Never trust a client-supplied tag id as "belongs to this user" — verify with `SELECT COUNT(*) FROM bookmark_tags bt JOIN bookmarks b ON bt.bookmark_id = b.id WHERE bt.tag_id = ? AND b.user_id = ?` before acting on it. `POST /bookmarks/tags/:id/favorite` enforces this scope; it also permits removal of the requesting user's stale favorite without disclosing a foreign tag name.
- Only remove the user's *own* `bookmark_tags` rows, never `DELETE FROM tags WHERE id = ?` unconditionally. Delete the `tags` row only when orphaned: `DELETE FROM tags WHERE id = ? AND NOT EXISTS (SELECT 1 FROM bookmark_tags WHERE tag_id = ?)`.
- `favorite_tags` is already per-user (`user_id, tag_id` PK), so clean up the requesting user's row there regardless of whether the global `tags` row gets deleted.

Merge (`POST /bookmarks/tags/merge`), rename (`PUT /bookmarks/tags/:id`, body `{ name }`) and delete (`DELETE /bookmarks/tags/:id`) share the statement builders `moveUserTagStatements`/`detachUserTagStatements` (plus `userTagUsageCount` for the ownership check); build the next per-user tag edit from them. Their orphan cleanup also requires that **no other user favorites** the row, because `favorite_tags.tag_id` is `ON DELETE CASCADE` and deleting the row would silently drop someone else's (stale) favorite. Rename never renames the global row: it upserts the new name (`upsertTagNamesStatement`), re-points only the user's links with `INSERT OR IGNORE` (so renaming onto a tag the user already uses merges without duplicate links; the response says `merged: true`), carries the user's favorite over (`keepFavorite`; merge does not), and cleans up the old row if orphaned. New names go through `normalizeTagName`, the same trim/lowercase/single-word/length rule as bookmark tags. Tag names match case-sensitively, so a legacy mixed-case row (`Recipes`) can be renamed to its lowercase form; a name equal to the current one after normalizing is a 400. Both routes answer 404 for a tag the user doesn't use (never revealing its name), validate the id and body first (400), and commit in one batch; `tests/tag-rename-delete.test.mjs` covers the tenant isolation.

## Bulk actions on the owner's library

`POST /bookmarks/bulk/delete` (`{ ids }`) and `POST /bookmarks/bulk/tags` (`{ ids, add?, remove? }`) sit in `handleBookmarks` before the `/:id/...` routes. Both go through `parseBulkBookmarkIds`: a non-empty array of positive safe integers, at most `INPUT_LIMITS.bulkBookmarkIds` (500, mirrored in `src/utils/inputLimits.js`; the web library caps its selection at the same number) **counted on the raw array**, then de-duplicated; anything else is a 400 before any SQL. `add`/`remove` go through `normalizeTagList` (same trim/lowercase/single-word rules as bookmark tags), at least one must be non-empty, and a name in both is a 400. Ids travel as one `json_each(?)` JSON parameter (D1 caps bound parameters at 100 per statement).

- **Ownership is in the SQL**, never a prior read: every statement carries `b.user_id = ?` for the ids (`OWNED_SELECTED_BOOKMARKS_SQL`). Policy for mixed lists: ids that aren't the caller's (or no longer exist) are **skipped** and only reported as a `skipped` count, indistinguishable from each other, so the route never confirms another account's id. It is not a 404/403 for the whole request, so a stale selection (deleted in another tab) still works.
- **Each action is one `db.batch()`**, atomic. `bulkDeleteBookmarks(db, userId, ids)` is the single place a bulk delete happens: **permanent**, like the single delete, and meant to be swapped for a soft delete when the trash feature (#61) lands without touching the route. Its batch runs, in order, the orphan cleanup of global `tags` rows (it has to read the links before they go: tags referenced only by the deleted bookmarks, no other bookmark link, no favorite by any account, the same orphan rule as tag delete and reset), the explicit `bookmark_tags` delete, then the bookmarks delete (`deleted` = that statement's `meta.changes`). The single `DELETE /bookmarks/:id` and `PUT` do not clean up orphaned tag rows (they are harmless: `tags/all` joins through links); the bulk routes do, because they can orphan many at once.
- **Tag changes** (`bulkChangeBookmarkTags`) upsert the `add` names, link them with `INSERT OR IGNORE`, unlink `remove` names from the caller's selected bookmarks only, then drop removed names that nothing references (links or favorites). `updated_at` is refreshed only on bookmarks that actually change, like a single edit. The per-bookmark cap (`tagsPerBookmark`) is enforced **inside the link statement** (existing tags plus new names not yet on it must fit), so a concurrent edit can't slip past a read; a bookmark that would overflow is left alone and counted as `overLimit` while the rest still change. `matched`/`overLimit` in the response come from a read just before the batch and are informational (the batch's guards are the control; the test harness's batch cannot return SELECT rows, which is why it isn't a batch statement).
- No profile-cache purge, same as single edits and deletes (the 60 s TTL covers it; see "Public profile edge cache").
- **UI**: `BookmarkBrowser` takes a `bulkActions` prop (`maxSelection`, `onDelete`, `onTags`, `onExport`); only `App.jsx` passes it, so public profiles never get select mode. The selection is a set of ids that survives paging and sorting but is **cleared whenever a filter changes** (the count must never include bookmarks you can't see); it is also intersected with the current result set every render. `renderCard` receives `selection: { selected, onToggle }` (null outside select mode) and `renderOwnerCard` draws the labelled checkbox. `BulkBar.jsx` is the toolbar (`role="toolbar"`, arrow/Home/End keys on top of Tab order), a `role="status"` count, and inline panels (tags form, export formats, tab-open confirmation/limit/blocked list, permanent-delete confirmation that states the exact count and focuses Cancel). Destructive confirmations are inline, not `window.confirm`, so the a11y audit can scan them. Export reuses `serializeBookmarks` through `downloadBookmarks` (also used by Settings → Export), filtered client-side from the already-loaded list; there is no server export route.
- **Open in tabs** (`src/utils/bulkOpen.js`): only `http:`/`https:` URLs; more than 10 asks first, more than 50 is refused. `openUrlsInTabs` runs synchronously inside the click (no `await` first) with plain `window.open(url, '_blank')` and cuts `opener` afterwards, because the `noopener` feature makes `window.open` return null even when it worked, which would hide blocked pop-ups. Blocked URLs come back as ordinary `target=_blank rel=noopener` links. Browsers commonly allow only the first pop-up (or a few) per click, so expect the blocked list for larger selections until the user allows pop-ups for the site; this was not measured per browser.

Tests: `tests/bulk-bookmarks.test.mjs`.

## Token revocation: `requireAuth` re-reads the user

Admin account deletion goes through `deleteAccount` (issue #11). Migration `0018`
adds `users.deletion_started_at`; the delete route fails closed before it exists.
The durable marker blocks sessions in `requireAuth` and new logins after password
verification. Never clear it automatically after a failure: Stripe may already
have stopped billing. Retry the admin delete to finish. Stripe customer deletion
cancels all its active subscriptions; subscription-only legacy rows use explicit
cancellation. Only a structured Stripe `resource_missing` 404 counts as an absent
resource, and success bodies are checked. The cleanup is one D1 batch, including
email-change tokens, user/email-linked auth events, and unused tag names; other
users' bookmarks and favorites must survive. Optional older tables/columns are
detected. `saveStripeCustomerId` conditionally refuses a new customer once deletion
has started (or the row is gone) and removes that unused customer, so a checkout
already in flight cannot attach new billing. Keep that guard on every new
customer-creation path. Tests: `tests/account-deletion.test.mjs`.
Webhook updates and billing-state clearing also guard the marker in their SQL,
so requests already in flight cannot replace/remove the billing IDs needed for
deletion. Keep those conditions atomic rather than relying only on a prior read.

Owners delete their own account through `POST /auth/delete-account` (issue #153;
Settings → Delete Account). It is `deleteAccount` behind `requireAuth`, a body of
`{ password, confirmation }` (the shared `ACCOUNT_DELETION_CONFIRMATION` word from
`src/utils/accountDeletion.js`, validated server-side) and `confirmCurrentPassword`,
called after the cheap checks and after the protected-super-admin refusal
(`isProtectedSuperAdmin`, 403, shared with the admin route). Both self-service routes
finish in `finishSelfServiceDeletion`: on success it purges the profile cache and
clears the session cookie; on a failure **after** the marker is stamped (a re-read
of the row decides, so failures before it, like a missing migration, stay ordinary
errors with the session intact) it answers 502/503 with `deletionPending: true` and
also clears the cookie, because `requireAuth` already rejects that session. Resuming
is `POST /auth/resume-deletion` `{ email, password }`: the credential half of login
is the shared `verifyLoginCredentials` (per-IP cap, user or unknown-address
lockout, same 401/429 bodies), so it shares the login counter and never reveals an
account before the password is proved; only then does it say 409 (nothing pending),
403 (super admin) or retry `deleteAccount`. Login itself answers a pending account's
correct password with 403 `{ deletionPending: true }` (checked before the
email-verified check). Neither route ever clears `deletion_started_at`, and none may
add a way to restore access while Stripe's state is uncertain. The web app lands on
`Home.jsx` afterwards (router state `accountNotice`: `deleted` or `pending`, read in
an effect so hydration matches the SSR'd markup) and offers "Finish deleting my
account". Tests: `tests/self-service-deletion.test.mjs`. Support recovery for a stuck
deletion is in `docs/deployment.md`.

Account reset (issue #154) is the library-only counterpart: `POST /auth/reset-library`
`{ password, confirmation }`, confirmation word `RESET` (`src/utils/accountReset.js`, shared with
the Settings form and deliberately not `DELETE`). It never calls `deleteAccount` and makes no
Stripe or email calls. Order: `requireAuth`, cheap validation, a re-read of the user row (409
when `deletion_started_at` is set; `requireAuth` already 403s a marked account, this closes the
race), `confirmCurrentPassword`, then `collectProfileCacheKeys` BEFORE one `db.batch()` of
`resetLibraryStatements` and `purgeProfileCacheKeys` after it. The batch is: delete the global
`tags` rows only this user references (their bookmark links or favorites, and no other user's
link or favorite, the same orphan rule as tag delete and `deleteAccount`) **first**, because that
subquery reads the user's links, then their `bookmark_tags`, `bookmarks` and `favorite_tags`
(guarded by `tableExists`). The bookmark count in the response is the bookmarks statement's
`meta.changes`; link and favorite counts are read just before the batch (the tag delete cascades
into links, so their `changes` would undercount). A batch failure is a 503 with nothing changed
and the session intact. It keeps users, sessions/`token_version`, `api_keys`, preferences,
`profile_public` and billing columns untouched; if you add a new per-user library table, add it
to `resetLibraryStatements` and to `deleteAccount`. The Settings tab refreshes the bookmark
list through the `onImportComplete` prop. Tests: `tests/account-reset.test.mjs`.

`requireAuth` verifies the JWT and then loads the `users` row on every request, rejecting the token if the account is gone or its `tv` claim doesn't match `users.token_version`. `auth.user` is built from that row, not from the token payload. Call `bumpTokenVersion(db, userId)` to sign a user out everywhere — password change and password reset already do. If the current session should survive (as with password change), sign a fresh token with `signUserToken(user, env, request)` and return it through `sessionResponse(request, data)`; web clients receive a replacement cookie, bearer clients a JSON token. Tokens issued before `0011_token_version.sql` have no `tv` claim and count as version 0.

JWT validation goes beyond the signature: `jwtVerify` pins HS256 and requires `exp` + `iat` (every token ever issued has both), and `hasValidSessionClaims` requires an integer `id`, an integer `tv` if present, `session` absent or `'web'`, `iat` not in the future, and `exp - iat` no longer than the type's lifetime (7 days web, 60 days bearer, plus 60s skew). `signUserToken` has issued `iss: 'tagsta.sh'` / `aud: 'tagstash-api'` since this change, but they are only checked **when present**: bearer tokens without them stay valid for up to 60 days after the deploy that started issuing them. After that window, make them required (`issuer`/`audience` options on `jwtVerify`). Lengthening a session type means raising its cap in `hasValidSessionClaims` too.

The web app sends `X-Tagstash-Client: web` and uses seven-day HttpOnly cookie sessions (`__Host-tagstash-session`, `Secure`, `SameSite=Lax`, no Domain; HTTP loopback uses `tagstash-session` without Secure). The extension still uses 60-day bearer JWTs. `session: 'web'` JWTs are cookie-only; all other JWTs are bearer-only. `onRequest` enforces the custom header and trusted web Origin/Referer/Fetch Metadata on web requests and cookie mutations, exempting the signature-verified Stripe webhook. Do not broaden credentialed CORS to extension or arbitrary origins. The public profile client omits credentials because its stable API keeps wildcard CORS. `POST /auth/session` upgrades legacy web bearer tokens; `POST /auth/logout` clears the cookie. No new session tokens are stored in localStorage.

## Brute-force protection and the `auth_events` log

`0012_login_protection.sql` adds `users.failed_attempts`/`locked_until` (epoch ms) and an `auth_events` table. Login locks an account for 15 minutes after 8 wrong passwords (`recordFailedLogin`, checked via `getLockedUntil` *before* bcrypt), a successful login or password reset clears it, and a locked login answers **429**. Per-IP and per-email caps live in the `AUTH_RATE_LIMITS` table and are counted from `auth_events` by `isAuthRateLimited`; `recordAuthEvent` writes the row, prunes rows older than 30 days, and never throws. Its `console.warn` carries only the event type and internal user id: raw emails and IPs belong in the access-controlled `auth_events` table (disclosed in `PolicyPage.jsx` as the 30-day security log), never in Worker logs. Don't add `console.log` lines that print emails, IPs or whether an account exists; `tests/auth-log-privacy.test.mjs` checks this. Both helpers fail open before the migration is applied, and the lockout helpers read the `SELECT *` user row so absent columns are a no-op — no PRAGMA guard needed on the login path.

The per-account counter is atomic: `recordFailedLogin` increments and locks in one `UPDATE … RETURNING` (never read-modify-write), leaves an already-locked row untouched, and the login handler re-reads `locked_until` after a correct password so a guess in flight during the locking misses is refused. The `AUTH_RATE_LIMITS` event caps are count-then-write **soft limits** that a simultaneous burst can overshoot; the lockout is the hard control. `tests/login-lockout.test.mjs` covers the races.

Routes that re-ask for the current password (`PUT /auth/username|email|password`) must go through `confirmCurrentPassword`, never a bare `bcrypt.compare`: it shares the login counter/lock and the per-IP cap (its failures are logged as `password_confirmation_failed`), and a correct password clears the counter. Call it after cheap input validation so malformed requests don't spend budget. A stolen session guessing therefore also locks the owner's login for 15 minutes; a password reset lifts it.

Throttles are checked **before** the user lookup and count unregistered emails too, so a 429 never reveals whether an account exists — keep it that way when adding limits. Verification resends have per-address caps (`verificationResendsPerEmail` 5/hour, `verificationResendsPerEmailBurst` 1/minute) in place of the old per-account "wait a moment" 429 that only real unverified accounts could trigger. See "Account enumeration" below. Super admins see the log in Settings → Admin (`GET /api/auth/admin/auth-events`, which hides the high-volume `register_attempt`/`verification_resend_requested` rows). `CF-Connecting-IP` is absent in local dev, so per-IP limits don't apply there unless you send the header yourself.

A Cloudflare rate-limiting rule on `/api/auth/login` sits in front of this as a supplement; its block page is HTML, not JSON, which is why `describeAuthError` in `AuthContext.jsx` has a 429 fallback message.

## Account enumeration: private emails never leak, public usernames may

Usernames are public (profile URLs); email addresses are not. No unauthenticated route may reveal whether an email has an account, whether by body, status, the order of checks or (where reasonably avoidable) timing:

- **`POST /auth/register`** validates input, answers 503 when email isn't configured (the same for every address), applies the per-IP cap, checks the **username** (400 "That username is already taken": public information, checked before and independently of the email), runs the breach check, always computes the bcrypt hash, then runs one conditional `INSERT … SELECT … WHERE NOT EXISTS (email or username)`. Inserted or not, the answer is the same `201 REGISTRATION_ACCEPTED_RESPONSE`. Both emails go out **after** the response: a new account's token and verification email (`sendNewAccountVerification`), or the existing owner's notice (`notifyExistingAccountOwner` → `sendExistingAccountNotice`). The notice goes out at most `registrationNoticesPerEmail` (3) times per address per 24 hours, is logged as `register_owner_notified`, and is skipped silently over the cap. As a result, registration no longer reports a failed verification send as a 502. **Never delete the new account when the background token write or send fails**: the caller has already been told to check their email, and "Resend verification email" (or forgot-password) is how they recover, which only works if the unverified account still exists. A failed send drops its undelivered token, so the resend route's "link issued under a minute ago" skip doesn't swallow the retry; the failure is logged by error type only.
- **`POST /auth/forgot-password`** and **`POST /auth/resend-verification`** throttle by IP and address before any lookup and record the request. The lookup, the "a link was issued less than a minute ago" check (now a silent skip, not a 429), token rotation and the send all happen after the response. Every address gets the same body.
- **`PUT /auth/email`** checks "Email is already in use" only **after** `confirmCurrentPassword`, so a stolen session can't probe addresses. A signed-in owner who knows their own password still can, one confirmed request at a time; that is accepted.
- **Login** answers "Invalid email or password" with a dummy bcrypt compare for unknown addresses, and an unknown address **locks out exactly like a registered one** (8 misses, 429 for 15 minutes with the same "N minutes" wording, no hashing while locked), so tripping the lockout can't probe for accounts (issue #140). With no `users` row to count on, `recordUnknownEmailFailedLogin` / `getUnknownEmailLockedUntil` keep the state in `auth_events`: `login_failed` rows and an `account_locked` marker with `user_id` NULL per normalized email, with millisecond `created_at` stamped from the **Worker clock** (bound as a parameter, never SQLite's `'now'`: D1's clock can differ from `Date.now()`, which real accounts' `locked_until` uses, and any gap would change the "N minutes" wording and leak existence; `tests/account-enumeration.test.mjs` skews the clock to pin this). Each miss's rank is its row's position among counted failures since the last lock expired, so concurrent bursts behave like the atomic `UPDATE … RETURNING` (exactly the 8th miss reports the lock). Only this path reads those rows, so a later registration of the address starts clean and no real account can be locked through it. Nothing new is stored (the same email/IP columns `login_failed` always wrote). Unlike the users counter, the unknown-address count cannot outlive the 30-day pruning. Keep every branch doing the same hashing work and giving the same status, body and headers.

"After the response" means `runAfterResponse(context, label, task)`. It hands the task to Pages Functions' `context.waitUntil` (threaded `onRequest` → `routeRequest` → `handleAuth(request, env, segments, context)`); without `waitUntil` (other runtimes, most tests) it awaits inline. It catches failures and logs only the error type, so a provider error reaches neither the caller nor the log with an address in it. Use it for any new email that only some addresses would trigger. Tests pass `waitUntil` through `call(env, path, { waitUntil })` in `tests/helpers/api.mjs`, and `tests/account-enumeration.test.mjs` holds sends open to prove responses don't wait for them.

## Password policy: one helper for every password setter

`validateNewPassword(password, { label })` in `functions/api/[[path]].js` is the only way a new password is accepted (register, `PUT /auth/password`, `POST /auth/reset-password`). `passwordPolicyError` is its synchronous half, called early so malformed input never spends a rate-limit slot or an upstream call. The length rules themselves are **one module shared by the API and the web forms**: `src/utils/passwordPolicy.js` (`newPasswordError`, `NEW_PASSWORD_HINT`), which the Worker imports (the same way `functions/index.js` imports from `src/content/`) and `Home.jsx`, `Settings.jsx` and `ResetPassword.jsx` use for early errors and hint copy. Change the rules there, never in a copy. The policy (product owner decision, issue #7):

- **At least 8 characters**, counted as code points (`[...password].length`), so an emoji counts once.
- **At most 72 UTF-8 bytes**, measured with `TextEncoder`, not `.length`. bcrypt hashes only the first 72 bytes, so a longer password would be silently truncated and any password sharing that prefix would sign in. Only the too-long error explains bytes vs characters; the form hint (`NEW_PASSWORD_HINT`) stays short and names just the minimum and the breach check. Client fields carry `minLength` but **no `maxLength`**, because a browser silently truncates pasted text at `maxLength` (the same bug). The numbers live in `src/utils/inputLimits.js` and are repeated in the server's `INPUT_LIMITS` (the drift test pins them).
- **Not in a known breach**: `isPwnedPassword` SHA-1s the password and sends only the 5-character prefix to `https://api.pwnedpasswords.com/range/<prefix>` with `Add-Padding: true`. It compares suffixes locally and ignores padding rows (count 0). It runs after the cheap checks, and on change/reset only after the current password or a live reset link has been proved. It **fails open** (3-second timeout, network error, non-2xx), logging only the error type. Never log or store the password, its hash, the suffix or the response. The Privacy Policy's Third-Party Services section discloses it.
- **Grandfathering**: login and `confirmCurrentPassword` never apply the policy. Any stored password that matches its hash keeps working, however short or long. Setters allowed up to 256 characters (and before v1.31.1 had no maximum), so some stored passwords exceed 72 bytes and still compare on their first 72 bytes, as they always did; for those accounts a different password with the same first 72 bytes also signs in until the owner sets a new password. Don't add a length check to login or re-entry: it would lock those owners out.

Tests: `tests/password-policy.test.mjs`. `tests/helpers/auth-env.mjs` installs a default `fetch` stub that answers Pwned Passwords with a padding-only range ("not found"), so tests never reach the real service. A test that installs its own `fetch` must answer `api.pwnedpasswords.com` too (or let the check fail open).

## Personal API keys are not (yet) an auth path

Settings lets users generate/revoke personal API keys (`api_keys` table, `0001_initial.sql`; routes at `GET/POST /api/auth/api-keys`, `DELETE .../api-keys/:id` for revoke, `DELETE .../api-keys/:id/permanent`). Keys are stored **hash-only** (`hashApiKey`, SHA-256) plus a non-secret `key_prefix`/`key_last4` display hint: `POST` returns the plaintext exactly once, and `GET` returns metadata only (`toApiKeyMetadata`). Never reintroduce reversible storage or put key material in a list response. The old AES `encrypted_key` column is legacy: no code reads or writes it, and `0015_api_keys_hash_only.sql` nulls existing values (old keys stay valid as hashes but can't be redisplayed). `API_KEY_ENCRYPTION_SECRET` is no longer used. `POST` refuses a new key once a user has `MAX_ACTIVE_API_KEYS_PER_USER` unrevoked keys. Despite existing, these keys are **not currently wired into `requireAuth`** (the README says so too — keep it honest) — that helper accepts JWT bearer tokens or web session cookies. Don't assume a route documented as requiring auth accepts an API key; it doesn't yet.

## Super-admin role is config-driven, not just a DB flag

`requireSuperAdmin(db, authUser, env)` gates the admin routes (`GET/PATCH/DELETE /api/auth/admin/users*`, the moderation `POST /api/auth/admin/users/:id/{suspend|unsuspend|make-private}`, and `GET /api/auth/admin/auth-events`). On every check it cross-references `SUPER_ADMIN_EMAIL` (and any other configured role mapping) via `isSuperAdminEmail`/`getRoleForEmail`, and self-heals `users.role` to match via `ensureUserRoleMatchesConfig` — so a configured super-admin's role can't be permanently changed through the admin API itself; it'll just resync on the next check. Changing who's a super-admin means changing env config, not just editing the `users` row.

## Profile moderation and the indexing bar

Visibility rules for public profiles live in one module, `functions/_lib/profileVisibility.js` (no `onRequest*` export, so Pages doesn't route it), imported by `GET /api/profiles/:username`, the `/u/:username` SSR and the sitemap. Don't re-derive them inline in one of the three.

- **Visible** = `profile_public = 1` and not suspended. Missing, non-public and suspended profiles all get the *same* 404 (SSR and API); never reveal that an account is suspended.
- **Indexable** = visible and passes `PROFILE_INDEXING_BAR`: verified email, account ≥ 14 days old, ≥ 5 public (non-private) bookmarks. Only indexable profiles are in `/sitemap.xml`. Only indexable profiles get the server-rendered bookmark snapshot (`#ssr-profile`) in `/u/:username`'s initial HTML; below-bar, missing, non-public and suspended ones get none. A visible but below-bar profile still renders **200** with `<meta name="robots" content="noindex">` and `X-Robots-Tag: noindex`. Going public is still immediate; the bar only governs indexing. Change the thresholds in that constant only.
- The API returns `profile.indexable` (an additive field) so `PublicProfile.jsx` passes the same `noindex` to `useDocumentMeta` as the SSR. Without it, hydration would remove the server's robots meta. It discloses nothing the page's robots meta doesn't already say.
- **Suspension** (`users.suspended_at`/`suspended_by`, migration `0016`): set by `POST /api/auth/admin/users/:id/suspend`, cleared by `.../unsuspend`. Suspending bumps `token_version`, so every existing web and extension session is signed out; the user can still sign back in and use their private library (non-destructive and reversible). `PUT /auth/profile-public` refuses to turn the profile **on** (403 `{ suspended: true }`) but always allows turning it off. `/auth/me` returns `suspended` so Settings → Public Profile can show a notice. Suspending does **not** touch `profile_public`, so lifting a wrongful suspension restores the profile as it was. `.../make-private` sets `profile_public = 0`, and unsuspending never re-publishes it. Super admins can't be suspended.
- Moderation actions go to `auth_events` (`admin_account_suspended`, `admin_account_unsuspended`, `admin_profile_made_private`) with `actor_user_id` naming the admin (also `0016`), shown with a "By admin" column in Settings → Admin. Like every `auth_events` row they're pruned after 30 days; `users.suspended_by` keeps the current suspension's actor.
- Before `0016` is applied: nobody counts as suspended, suspend/unsuspend answer 503, `make-private` still works (it only needs `profile_public`), and events are logged without an actor.
- "Report this profile" on public profiles links to `/support?report=<username>`. `SupportPage` prefills the message with the profile URL; it accepts only a username-like value.

## Changing an account's email is a two-step, inbox-verified flow

`PUT /auth/email` never writes `users.email`/`role`. After the password check it stores a hashed token in `email_change_tokens` (`0014`, fail-closed 503 until applied), mails the link to the **new** address and warns the old one. The link reuses `/verify-email?token=`: `confirmEmailChange` claims the token atomically (signup verification does the same, claiming the token and marking the account verified in one batch; it also issues **no session**, so a leaked link never signs anyone in), then sets email + `getRoleForEmail` role, clears the user's reset tokens, bumps `token_version`, and issues **no session** (the frontend shows "sign in again"). Keep role promotion behind this confirmation — an unverified address must never change effective privileges.

## Frontend: real client-side routing (react-router-dom)

`src/main.jsx` wraps the app in `<BrowserRouter>`, and `src/App.jsx` (the always-mounted root) renders a `<Suspense><Routes>…</Routes></Suspense>` tree using `useNavigate`/`useParams`/`useSearchParams` — there's no manual `activePage` string or `window.location.pathname` parsing.

## Shared bookmark-browsing UI and app shell

`src/components/BookmarkBrowser.jsx` owns sort/search/tag/domain/month-filter/pagination state and renders the toolbar + grid + pagination + sidebar `TagCloud`. Both the owner's main view (`App.jsx`) and the public profile (`PublicProfile.jsx`) render it — **don't fork this logic again** for a future read-only or filtered view; add a prop instead. Existing extension points: `renderCard`, `toolbarExtra`, `showFavoritesFilter`, `showUntaggedFilter`, `showDomainFilter`, `showDateFilter`, `tags`, `emptyStateMessage`, `initialSelectedTags`/`onSelectedTagsChange`, `focusBookmarkId`, `bulkActions` (owner-only multi-select; see "Bulk actions on the owner's library").

`showDomainFilter` and `showDateFilter` default off; `App.jsx` enables both, and public profiles leave them off. The native sidebar pickers use counts from the whole supplied list. Domains share `getBookmarkDomain`/`countDomains` in `src/utils/bookmarkFilters.js` with the owner's Related button: HTTP(S) URLs grouped by `getRegistrableDomain` in `src/utils/domain.js` (one copy of the original `MULTI_PART_TLDS` list). Subdomains share a site (`www.reddit.com` and `old.reddit.com` → `reddit.com`; `old.reddit.co.uk` → `reddit.co.uk`). `URL` canonicalizes case and IDNs and strips ports; IP literals keep their complete address. The suffix list is intentionally the existing approximation, not a full public suffix database. Related replaces all filters with that domain; selecting a domain in the picker combines with search, tags, favorites, untagged and month. Month options include the year, newest first, from `created_at`; missing/invalid dates are omitted. D1's offset-free timestamps are interpreted as UTC instants, then bucketed using the visitor's **local time zone**, so UTC midnight can land in the previous local month. The helpers are unit-tested across time zones. Each picker has an All option and an active chip with its own clear button; Clear all filters and Random reset both. They are client-side only, never in the URL or public API.

`focusBookmarkId` short-circuits all browsing filters to show only that bookmark (clearing the underlying filter controls as a side effect) and scrolls it into view once rendered — it's how the "Random" toolbar button isolates a single bookmark in edit mode regardless of the active filter. Clear it back to `null` (on cancel/save/refresh) to return to the full list.

`showUntaggedFilter` (default off; `App.jsx` turns it on, `PublicProfile.jsx` doesn't, since visitors browse by tag and the toggle is owner housekeeping) renders a "Without tags (N)" toggle button above the tag rack in the sidebar; the count comes from the whole list, not the current filters. It is client-side state only (`hasNoTags`/`countUntagged` in `src/utils/bookmarkFilters.js`, unit-tested), mutually exclusive with tag selection (picking a tag, from a card or the rack, clears it; turning it on clears selected tags), and combines with search, favorites, domain and month. "Clear all filters", Random and Related reset it. If there are no untagged bookmarks at all, turning it on shows an "Every bookmark has at least one tag." empty state instead of the generic "No bookmarks match". Like the other filters it is not in the URL (only the public profile mirrors tag selection to `?tag=`).

`TagCloud.jsx` accepts an optional `tags` prop so it can be fed pre-fetched data instead of self-fetching via the authenticated `/api/bookmarks/tags/all`, and an optional `showActions` prop (default `true`) that hides the add-to-query/favorite icon row where the chips are just a pick-list — `TagsPage.jsx`'s merge picker is the reference usage (`showActions={false}`, `onTagSelect` repurposed to mean "select as source/target" instead of "filter by this tag"); the "Rename or Delete a Tag" section (`TagEditSection.jsx`) uses a second picker the same way. Its destructive steps (delete, and a rename that would merge) confirm **inline** (a focused confirmation group with Confirm/Cancel) rather than with `window.confirm`, so the a11y audit can scan them; the merge picker still uses `window.confirm`. Each rack tag is a noninteractive `.tag-stock` wrapper holding **sibling** native buttons — the name (`aria-pressed`, select), add-to-filter, and favorite (`aria-pressed`). Never nest the action buttons inside an interactive parent (axe `nested-interactive`; a parent key handler swallows their Enter/Space), and keep every chip control at least 24×24 CSS px (WCAG 2.5.8 / axe `target-size`).

`App.jsx`'s bookmark list has a manual refresh button plus a silent 5-minute `setInterval` poll (mirroring the extension sidebar's interval). There is **no** push/webhook/websocket between a bookmark save (e.g. from the extension) and an already-open web app tab — both are plain re-fetches of `GET /bookmarks` + `GET /bookmarks/tags/all`. Don't assume the UI reflects extension-side changes immediately.

`normalizeBookmarkUrl` is duplicated three times — `src/App.jsx`, `functions/api/[[path]].js`, and `../tagstash-extension/lib/bookmark-url.js` — rather than shared, since the extension is a separate deployable with its own bundling. It prefixes a missing `https://` and keeps a trailing slash on bare roots (`https://example.com` → `https://example.com/`); deeper paths are left alone. The "Base URL" button (`handleBaseUrl`/`handleEditBaseUrl` in `App.jsx`, `toBaseUrl` in the extension's `lib/bookmark-url.js`) relies on the same root selection via `new URL(...).origin + "/"`. **Change one copy, change all three**, or site and extension will silently disagree on what gets stored for the same pasted URL.

`src/components/AppHeader.jsx`/`AppFooter.jsx` are the shared page chrome (logo, tagline, theme selector, footer copyright) used by every full-page view. `AppHeader` takes an optional `onLogoClick` — pass it for the authenticated button-based "back to bookmarks" behavior, omit it for a plain `<a href="/">` logo link on anonymous/public pages. Page-specific actions (welcome text, nav buttons, logout, footer links) go through each component's `children`, not by forking the markup.

## Theme system: three CSS-variable themes, account-synced

Three themes — `slate` (neutral grey, default), `midnight` (the original purple-heavy dark theme), and `light` — are three blocks of CSS custom properties in `src/index.css`: bare `:root` (slate), `:root[data-theme='midnight']`, `:root[data-theme='light']`. Every themed color goes through a `--color-*`/`--shadow-*`/`--theme-gradient` variable; there should be no hardcoded theme-sensitive colors in component CSS. `slate` intentionally keeps the purple accent variables matching `midnight` so buttons/links/tags stay on-brand — only neutral surface/background/border/text variables and `--theme-gradient` differ between the two dark themes.

Tags everywhere (cards, tag rack, filters, tag inputs, Tags page, home demo) render with the shared `.tag-stock` class in `index.css`: a soft-violet shipping tag (echoing the logo) with a pointed end and a punched eyelet, colored per theme by `--color-tag-bg`/`--color-tag-bg-hover`/`--color-tag-edge`/`--color-tag-ink`/`--color-tag-ring`, with `.tag-stock--active` for selected (solid violet). Keep `--color-tag-bg` opaque: the point is a separate pseudo-element, so a translucent fill shows a seam where they meet. The eyelet is painted with `--tag-eyelet`, which must match the surface behind the tag (it defaults to `--color-panel`); override it when a tag sits on a different surface. Type is a single family, Archivo, **self-hosted** from `src/assets/fonts/` (SIL OFL 1.1; license text sits alongside and is published at `/archivo-OFL.txt`): `@font-face` rules at the top of `src/index.css`, one woff2 per Google unicode-range subset (latin, latin-ext, vietnamese), `font-display: swap`. The files are the variable font instanced to the ranges the CSS uses, `wght` 400-800 and `wdth` 100-118 (`--stretch-display`), so a weight outside 400-800 or a width past 118% means regenerating them (fonttools `varLib.instancer` on the Google Fonts woff2, then update the `font-weight`/`font-stretch` descriptors). `index.html` preloads the latin file; Vite rewrites that href to the hashed `/assets/` URL (the same file the CSS references, so it is fetched once), and the prerendered pages and the SSR'd `/` and `/u/*` inherit the tag from the built shell. Type is expanded via `--stretch-display` for headlines, normal width everywhere else (tag labels were condensed at first and proved hard to read; keep them at normal width and at least ~0.8rem).

Contrast: text on the tinted banners (`.auth-error`, `.settings-error`, `.settings-success`, `.tag-merge-preview`) uses `--color-danger`/`--color-success` over the `*-soft` fills, and muted copy uses `--color-text-muted`; in `light` those values were tuned to clear 4.5:1 on their real backgrounds (re-check with `npm run test:a11y -- --contrast-report` before lightening them). Solid fills that carry white text use `--color-danger-solid`/`--color-danger-solid-hover`/`--color-success-solid`, not the text-tone variables (the dark themes' `--color-danger` is a light pink that fails against white). Don't dim text with `opacity`; use a color variable so the ratio is predictable. The cookie banner's Accept and Decline share `.cc-btn` on purpose (equal prominence for consent); don't restyle one as primary.

`THEME_ORDER`/`THEME_LABELS`/`THEME_ICONS`/`isValidTheme` live in `src/utils/theme.js`, the single source of truth — import from there rather than hardcoding theme name lists. `src/components/ThemeSelector.jsx` renders the header control: collapsed it shows the active theme's icon, and hovering/focusing expands it (via a JS `expanded` state, not pure CSS `:hover`, so keyboard focus and touch tap work too) into all three options in **fixed** `THEME_ORDER` position — non-active buttons collapse to `max-width: 0` rather than being reordered, so selecting a theme never makes buttons swap places.

⚠️ If you touch `.theme-selector-btn` in `index.css`, watch for specificity traps: a `:first-child`-style override can silently beat a `--hidden`/`--collapsed` modifier of equal-or-lower specificity, leaving phantom padding on whichever button sits first in DOM order. Prefer uniform per-button padding plus a single collapse mechanism over position-based selectors.

`App.jsx` owns the state: `theme` (`useState`, initialized from `localStorage['tagstash-theme']` or `prefers-color-scheme`), applied via `document.documentElement.dataset.theme` in a `useEffect`. `selectTheme(nextTheme)` sets it directly (no cycling) and, when logged in, fires `authAPI.updateTheme(nextTheme)` (`PUT /api/auth/theme`, guarded by `usersTableHasColumn(db, 'theme')` per the migration pattern above) to persist to `users.theme`. A separate effect applies `user.theme` over the local value whenever `user` loads/changes — so a logged-in account's saved theme wins over `localStorage` on that browser, while logged-out visitors still get `localStorage`/system-preference behavior.

## Link-opening preference: same shape as theme, but don't share it with the extension

"Open bookmark links in a new tab / the same tab" (Settings → Preferences) is stored per account in `users.link_target` (`'new' | 'same'`, nullable — `NULL` means never picked), written by `PUT /api/auth/link-target` behind the usual `usersTableHasColumn(db, 'link_target')` guard, and returned by `/auth/login` and `/auth/me`. `App.jsx` owns the state exactly like `theme`: `localStorage['tagstash-link-target']` for first paint and anonymous public-profile visitors, overridden by `user.link_target` once the account loads.

`src/utils/linkTarget.js` is the single source of truth (`LINK_TARGET_ORDER`/`LINK_TARGET_LABELS`/`isValidLinkTarget`/`linkTargetProps`). Apply it by spreading `linkTargetProps(linkTarget)` onto the anchor rather than hardcoding `target="_blank" rel="noopener noreferrer"` — that helper is what drops both attributes for the same-tab case. It's meant for **bookmark URLs only** (the card link, the edit form's "Open" button); site chrome like the footer and marketing links stays `_blank` unconditionally.

The browser extension has its own equivalent setting (sidebar cog → "Open bookmarks in"), stored in `browser.storage.local` and **deliberately never synced with this one** — unlike `theme`, which the extension mirrors from the account. Don't "fix" that asymmetry by making the extension read `user.link_target`.

## Dependency installs

Use `npm ci` on a clean checkout. `.npmrc` sets a 7-day `min-release-age` and `strict-allow-scripts`; `package.json` `allowScripts` denies esbuild/workerd install scripts (not needed). ## Local dev workflow

```bash
npm run setup:db   # apply D1 migrations to local wrangler state
npm run dev:all    # Vite (localhost:3000) + wrangler pages dev (127.0.0.1:5000), proxied via /api
```

Gotchas:

- **Email verification can't be exercised locally** unless `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` are set in `.dev.vars` — `POST /api/auth/register` answers 503 without them (with them, a failed send after the response leaves the new account unverified, recoverable via "Resend verification email"). For a usable authenticated test account, insert a pre-verified user directly into local D1:
  ```bash
  node -e "require('bcryptjs').hash('testpass123', 10).then(console.log)"
  npx wrangler d1 execute tagstash-db --local --command "INSERT INTO users (username, email, password_hash, membership_tier, role, email_verified) VALUES ('testuser', 'test@example.com', '<hash>', 'free', 'user', 1)"
  ```
  then log in via `POST /api/auth/login` to get a JWT.
- **Auth regression checks:** `npm run test:auth` (Node 22.13+), using isolated in-memory SQLite with the real migrations and API handlers. For concurrency tests pass `createAuthEnv({ queryLatency: true })`: each query then waits a macrotask like a real D1 round trip, so parallel requests actually interleave. Without it they run back to back and check-then-act races pass by accident. Mock upstreams by replacing `globalThis.fetch`; `tests/upstream-calls.test.mjs` also shortens `AbortSignal.timeout` to exercise real deadlines quickly. General verification remains `npm run build` plus driving the app. Pure helpers in `functions/api/[[path]].js` (extractors, normalizers) can be exercised without a Worker by slicing the function out of the file into a temp `.mjs` and importing it — cheap way to check parsing changes against real fetched HTML.
- This environment has a working local Playwright setup (Chromium cached under `%LOCALAPPDATA%\ms-playwright\chromium-<rev>\chrome-win64\chrome.exe` — note `chrome-win64`, not `chrome-win`), usable via `playwright-core` installed ad hoc in the scratchpad. Useful for screenshotting/regression-checking both owner and public-profile views. For authenticated flows, drive login or call `/auth/login` with the web-client header and cookie-aware request context. Setting `localStorage['token']` now only exercises the legacy upgrade path.
- **Accessibility audit:** `npm run test:a11y` (`scripts/a11y-audit.mjs`) runs pinned axe-core (exact devDependency; 4.10.2) through pinned `playwright-core` + a cached Chromium against a **locally served build**, in slate, midnight and light, and exits 1 on any violation (tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`, plus axe `best-practice` for landmarks/`region`). Serve first: `npm run build`, then `npx wrangler pages dev dist --local --port 5000` (needs `.dev.vars` with `JWT_SECRET` and `SUPER_ADMIN_EMAIL=admin@example.test`, and `npm run setup:db`). The script seeds two local-only users (`a11yowner` with a public profile, six tagged bookmarks and one untagged one, and the super admin) with `wrangler d1 execute --local`, then logs in through the real login form. It scans anonymous pages (home incl. login error / sign-up / forgot-password states and the server-rendered markup with scripts blocked, `/features`, `/privacy`, `/support`, a public profile), owner views (`/` list incl. the "Without tags" filter active and its no-match state, the domain and month filters alone, combined with the other filters and with no matches, add form, edit mode, select mode (none selected, some selected, the tag form with a validation error and a refused request, export formats, tabs blocked by the browser, the delete confirmation and a refused delete, a selection cleared by a filter; every `/bookmarks/bulk/*` request is answered by an interception, so the seed is never changed); every `/settings` tab plus the error and success banners and the import preview; `/tags` with empty and selected merge slots, plus the rename form, a name error, a would-merge rename and both inline confirmations, all cancelled so the seed stays intact), the Settings → Reset Library form (idle, confirmation error, refused password, pending, success), the Settings → Delete Account form (idle, confirmation error, refused password, pending, and the hand-off to "finish deleting"), the signed-out "finish deleting your account" and "account deleted" pages, and Settings → Admin plus the super admin's Delete Account note. The deletion states answer from `page.route` interceptions (`interceptJson`), so no seeded user is ever deleted and the server is never asked to delete anything. The cookie banner is visible in every scan. Options: `--base-url`/`A11Y_BASE_URL` (default `http://127.0.0.1:5000`, loopback only; the script refuses anything else), `--themes`, `--roles`, `--skip-seed`, `--contrast-report` (prints measured ratios for the banner/label/button colors), `A11Y_CHROMIUM_PATH` to override the Chromium executable (default: newest `chromium-*` under `%LOCALAPPDATA%\ms-playwright`, `PLAYWRIGHT_BROWSERS_PATH` or `~/.cache/ms-playwright`), `A11Y_D1_PERSIST_TO` if your server uses `--persist-to`. Rules are never silently disabled: anything excluded goes in `KNOWN_EXCLUSIONS` in the script with a reason (currently empty). axe's "needs review" (`incomplete`) results are counted but do not fail the run; they still need a human pass, as do keyboard/screen-reader and zoom checks. There is no CI in this repo yet, so run it by hand before releasing UI changes; wiring it into trusted CI is still open (#40). When a scenario needs a new state, add it to the script instead of testing by hand once.
- Windows Git Bash and Node resolve `/tmp` differently (`/tmp/x` from bash isn't `C:\tmp\x` from Node) — write files Node needs to read into the scratchpad directory instead of `/tmp`.
